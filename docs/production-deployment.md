# Production deployment: host Nginx + containerized app

This guide targets a single Linux server with Docker Engine, the Docker Compose
plugin, and host-installed Nginx and Certbot. The Nginx site supports direct DNS
and Cloudflare proxying. For Cloudflare, follow the complete
[Cloudflare update commands](cloudflare-deployment.md) and use Full (strict).

```text
Internet → host Nginx :443
             ├─ React assets: /srv/D27_lookup_endp/var/www/frontend
             ├─ Django admin static: /srv/D27_lookup_endp/var/www/static
             ├─ authorized exports: /srv/D27_lookup_endp/var/data/batches/exports
             └─ API/admin → 127.0.0.1:18000 → Gunicorn container
                                                  └─ PgBouncer → PostgreSQL
                       lookup / file / alert workers → PgBouncer
```

Use **`compose.production.yaml` on its own**. Do not combine it with
`compose.yaml`: that file is the development stack and includes container Nginx.
Production has no Nginx container. The frontend is built in a short-lived Node
container; Python, PostgreSQL, PgBouncer, and all workers run in containers.

## 1. Prepare the server

Place the complete project in `/srv/D27_lookup_endp`, including `deploy/`, lockfiles, and
migrations. Use a versioned release of the source, excluding `.env`, local
`var/`, development data, and dependency directories. Keep the project path
stable: its bind mounts hold production CSVs and exports.

Install Docker Engine and its Compose plugin using
[Docker's instructions](https://docs.docker.com/engine/install/ubuntu/).
For an Ubuntu/Debian host, install the edge services:

```bash
sudo apt-get update
sudo apt-get install -y nginx certbot
cd /srv/D27_lookup_endp
docker compose version
```

Point the domain's A record at the server. Only publish an AAAA record if IPv6
works. Allow inbound TCP 80, 443, and your configured SSH port. Gunicorn binds
only to `127.0.0.1:18000`; neither PostgreSQL nor PgBouncer publishes a host port.
Outbound HTTPS must reach the lookup service and Discord.

The deployment files are configured for **d27desk.peoplegraph.co** and the
existing checkout at **/srv/D27_lookup_endp**.

The app publishes only `127.0.0.1:18000`, which does not overlap the published
ports in your supplied container list (8080, 3001, 8001, 4331). Container-only
ports such as `8000/tcp`, `5432/tcp`, and `6379/tcp` do not reserve those host
ports. Host Nginx shares its existing 80/443 listeners across domain-specific
server blocks; leave other sites enabled. Confirm no additional host service
uses 18000 before starting:

```bash
sudo ss -ltnp 'sport = :18000'
```

If 18000 is occupied by a service outside that list, change the host side of
`127.0.0.1:18000:8000` in Compose and every `127.0.0.1:18000` upstream in this
app's Nginx config to the same available loopback port.

## 2. Configure production environment

On a fresh installation, generate private secrets using a temporary container:

```bash
cd /srv/D27_lookup_endp
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD:/workspace" -w /workspace \
  python:3.12-slim python init_env.py
chmod 600 .env
```

The generator never overwrites an existing `.env`. Edit it, retain the generated
`DJANGO_SECRET_KEY` and `DB_PASSWORD`, and set:

```dotenv
DJANGO_DEBUG=0
DJANGO_ALLOWED_HOSTS=d27desk.peoplegraph.co
CSRF_TRUSTED_ORIGINS=https://d27desk.peoplegraph.co
TRUST_PROXY_HTTPS=1
SECURE_SSL_REDIRECT=1
DB_NAME=suppression
DB_USER=suppression
DISCORD_WEBHOOK_URL=https://discord.com/api/webhooks/REPLACE_ID/REPLACE_TOKEN
BATCH_LOOKUP_INTERVAL=1
BATCH_ACCEL_DOWNLOADS=1
BATCH_MAX_UPLOAD_BYTES=104857600
BATCH_MAX_NUMBERS=1000000
BATCH_MAX_OPEN_FILES=10
```

Use the actual Discord webhook URL. The DB password must remain a URL-safe token
containing only letters, digits, `_`, and `-`, as generated by `init_env.py`.
Production Compose enforces non-debug mode, HTTPS proxy trust, secure redirects,
PgBouncer runtime connections, and accelerated downloads. `APP_BIND` and
`APP_PORT` from the development `.env` are not used by production Compose.

Do not change the database password after initialization by editing `.env` alone:
the existing PostgreSQL role must be rotated too. Keep `.env` out of source
control and backups in private storage.

Define this helper in your deployment shell; recreate it in each new shell:

```bash
d27() { docker compose -f /srv/D27_lookup_endp/compose.production.yaml "$@"; }
```

The Compose project name is fixed as `d27-production`, so moving between shell
working directories does not create a different database volume.

## 3. Obtain the TLS certificate

First install the HTTP-only bootstrap config. Do not install the final HTTPS
config before its certificate exists.

```bash
cd /srv/D27_lookup_endp
D27_DOMAIN=d27desk.peoplegraph.co
sudo mkdir -p /var/www/letsencrypt
sudo cp deploy/nginx/d27-bootstrap.conf /etc/nginx/sites-available/d27
sudo ln -sfn /etc/nginx/sites-available/d27 /etc/nginx/sites-enabled/d27
sudo nginx -t
sudo systemctl reload nginx
sudo certbot certonly --webroot -w /var/www/letsencrypt \
  -d "$D27_DOMAIN"
```

Certbot prompts for a contact email and agreement to its terms. If another
site already owns this hostname, remove its duplicate server block before
reloading Nginx.

## 4. Build and start the containers

```bash
cd /srv/D27_lookup_endp
d27 config --quiet
d27 up --build -d
d27 ps -a
d27 logs --tail 50 init_storage frontend_build migrate backend
d27 exec backend python manage.py createsuperuser
d27 exec backend python manage.py check --deploy
d27 exec backend python manage.py showmigrations
```

`init_storage`, `frontend_build`, and `migrate` should exit with code **0**.
PostgreSQL and backend should become **healthy**, and the three workers should
stay running. Initial backend health checks can take about 30 seconds.

Startup prepares directory ownership, publishes the frontend, migrates through
the direct PostgreSQL connection, and collects admin static files. Gunicorn and
workers use PgBouncer for runtime reads and writes. No host Python or Node
installation is required.

Persistent paths:

| Data | Location |
| --- | --- |
| Database, raw API responses, audit trail | Docker volume `d27-production_postgres_data` |
| Original CSVs | `/srv/D27_lookup_endp/var/data/batches/sources` (private, mode 700) |
| Prepared exports | `/srv/D27_lookup_endp/var/data/batches/exports` |
| Built React frontend | `/srv/D27_lookup_endp/var/www/frontend` |
| Collected admin static files | `/srv/D27_lookup_endp/var/www/static` |

Host Nginx needs traversal permission on `/srv`, `/srv/D27_lookup_endp`, and the public
parent directories. Keep these directories traversable, typically mode 755;
keep `.env` at 600 and source CSV directories private. The initialization
container sets ownership inside the writable app paths. Do not run Django or
workers as root.

The deployment check can report `security.W021` because HSTS preload is
intentionally disabled. It must not report debug mode, insecure cookies,
missing SSL redirect, or missing HSTS. The supplied configuration enables a
one-year HSTS policy including subdomains; all names below the deployed hostname
must support HTTPS. Preload registration is a separate, deliberate decision.

## 5. Enable host Nginx

```bash
cd /srv/D27_lookup_endp
sudo cp deploy/nginx/d27-production.conf /etc/nginx/sites-available/d27
sudo nginx -t
sudo systemctl reload nginx
```

This is the only serving Nginx process. It handles TLS, SPA routing, admin static
files, CSRF-compatible forwarding headers, login/authenticated-lookup request
limits, and protected export downloads. **The public individual lookup endpoint
is not rate limited by the app or Nginx.** The upstream service may still return
HTTP 429, which the app reports as an unverified check. Nginx replaces incoming
forwarding headers before sending requests to Gunicorn. Keep port 18000 private. The site restores Cloudflare
visitor IPs only from Cloudflare's published IPv4/IPv6 ranges; other proxies
require their own trust configuration.

Upload requests allow a 100 MiB CSV plus multipart overhead; other requests are
limited to 16 KiB. If increasing `BATCH_MAX_UPLOAD_BYTES`, increase the upload
location's `client_max_body_size` accordingly.

Renew certificates automatically and reload Nginx after successful renewal:

```bash
sudo mkdir -p /etc/letsencrypt/renewal-hooks/deploy
sudo tee /etc/letsencrypt/renewal-hooks/deploy/d27-nginx >/dev/null <<'HOOK'
#!/bin/sh
set -eu
nginx -t
systemctl reload nginx
HOOK
sudo chmod 755 /etc/letsencrypt/renewal-hooks/deploy/d27-nginx
sudo systemctl enable --now certbot.timer
sudo certbot renew --dry-run
```

## 6. Verify before opening access

```bash
curl -I "http://${D27_DOMAIN}/lookup-record"
curl -I "https://${D27_DOMAIN}/lookup-record"
curl -i "https://${D27_DOMAIN}/api/history/"
curl -I "https://${D27_DOMAIN}/protected-batch-exports/not-a-file/result.csv"
d27 logs --tail 50 backend lookup_worker file_worker alert_worker
```

Expected results: HTTP redirects to HTTPS (308), the public page loads (200),
anonymous history returns 401, and direct export paths return 404. In a browser:

1. Check `/lookup-record` without signing in; submit a permitted test number.
2. Sign in, upload a small CSV, check progress, pause/resume, and download its
   completed export. Confirm its `sqGOOD,sqBAD` contents.
3. Verify the admin page and its styling, then sign out and confirm downloads
   require authentication.
4. Verify a Discord test notification in your configured channel. This sends a
   real message; use the smoke-test script below when ready.

```bash
d27 exec -T alert_worker python - <<'PY'
import json, os
from urllib.request import Request, urlopen
request = Request(os.environ['DISCORD_WEBHOOK_URL'],
    data=json.dumps({'content': 'D27 deployment notification test.',
                     'allowed_mentions': {'parse': []}}).encode(),
    headers={'Content-Type': 'application/json'}, method='POST')
with urlopen(request, timeout=10) as response:
    print('Discord HTTP status:', response.status)
PY
```

No production webhook is contacted by the automated test suite.

### API returns HTTP 400 while the frontend loads

Static HTML is served by Nginx, so it can work even if Django rejects the
request hostname. A healthy backend also does not prove that the public domain
is allowed: the internal health check uses the first configured allowed host.
Check the actual running Django settings without displaying secrets:

```bash
d27 exec backend python manage.py shell -c \
  "from django.conf import settings; print('ALLOWED_HOSTS:', settings.ALLOWED_HOSTS); print('CSRF origins:', settings.CSRF_TRUSTED_ORIGINS)"
curl -i http://127.0.0.1:18000/api/history/ \
  -H 'Host: d27desk.peoplegraph.co' -H 'X-Forwarded-Proto: https'
```

The direct request should return **401**, not 400. If the public domain is
missing, correct `.env` and recreate the app containers to load it:

```bash
cd /srv/D27_lookup_endp
sed -i 's/^DJANGO_ALLOWED_HOSTS=.*/DJANGO_ALLOWED_HOSTS=d27desk.peoplegraph.co/' .env
sed -i 's|^CSRF_TRUSTED_ORIGINS=.*|CSRF_TRUSTED_ORIGINS=https://d27desk.peoplegraph.co|' .env
d27 up -d --no-deps --force-recreate backend lookup_worker file_worker alert_worker
curl -i https://d27desk.peoplegraph.co/api/history/
```

A simple container restart does not reload changed environment variables. If the
direct request returns 401 but the HTTPS request returns 400, check the installed
Nginx site's `proxy_set_header Host d27desk.peoplegraph.co;` directive, then run
`sudo nginx -t` and reload Nginx. Do not set `ALLOWED_HOSTS=*` to bypass this check.

## 7. Back up and update

Back up PostgreSQL **and** `var/data/batches` together. Stopping app writers
briefly gives a consistent backup. Host Nginx remains running but API requests
will return 502 during this maintenance window. Wait for graceful worker stops;
do not force-kill an in-flight lookup.

```bash
cd /srv/D27_lookup_endp
umask 077
D27_BACKUP="/srv/d27-backups/$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -p "$D27_BACKUP"
d27 stop lookup_worker file_worker alert_worker backend
d27 exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > "$D27_BACKUP/database.dump"
d27 run --rm --no-deps -T --user root --entrypoint tar file_worker \
  -C /app/data -czf - . > "$D27_BACKUP/batches.tar.gz"
cp .env "$D27_BACKUP/environment"
```

Check that both backup commands succeeded before continuing. Save the matching
source release or release identifier, host Nginx configuration, and TLS recovery
information alongside the backups. Encrypt and copy backups off the server,
with access restricted because they contain phone numbers and raw responses.
Never use `docker compose down -v` on the production stack.

To finish a backup without deploying, run `d27 up -d`. To deploy an update,
install the reviewed release at the same path, retaining `.env` and `var/`, then:

```bash
cd /srv/D27_lookup_endp
d27 config --quiet
d27 build
d27 run --rm --no-deps init_storage
d27 run --rm --no-deps frontend_build
d27 run --rm --no-deps migrate
d27 up -d
d27 exec backend python manage.py check --deploy
d27 ps -a
sudo nginx -t
sudo systemctl reload nginx
```

Stop on any build, publish, or migration failure. Old hashed frontend assets are
kept for open browser tabs; the publisher replaces `index.html` atomically after
copying the new assets. Reclaim obsolete frontend assets during a planned
maintenance window, not while clients may still reference them. Code rollback
alone is safe only when migrations remain backward-compatible; otherwise
restore the matching database/files snapshot and source release.

## 8. Restore on a fresh replacement server

Install the matching source release, Docker and host Nginx. Restore the saved
private environment as `/srv/D27_lookup_endp/.env` with mode 600. With the same helper:

```bash
d27 build
d27 up -d --wait postgres pgbouncer
d27 run --rm --no-deps init_storage
d27 exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner --exit-on-error' \
  < /path/to/backup/database.dump
d27 run --rm --no-deps -T --user root --entrypoint tar file_worker \
  -C /app/data -xzf - < /path/to/backup/batches.tar.gz
d27 run --rm --no-deps init_storage
d27 run --rm --no-deps frontend_build
d27 run --rm --no-deps migrate
d27 run --rm --no-deps backend python manage.py shell -c \
  "from batches.queue import pause_all; pause_all('Restored backup; staff review required before resuming.')"
d27 up -d
```

These restore commands target an **empty replacement database**, not a running
installation. Reissue/restore TLS certificates and install the host Nginx config.
Review queue checkpoints before staff clears the global safety stop. Requests
performed after the backup can be repeated after restoring it; the external
endpoint has no idempotency contract. Public individual checks stay unavailable
while the global safety stop is active.

Monitor free disk space, container restarts, failed exports, the safety-stop
indicator, Discord delivery state, and certificate expiry. The current storage
layout is single-host. A 500,000-number file takes at least 5.8 days at the
one-request-per-second batch gate, and stored responses can consume hundreds
of MB per file. Size retention and backups accordingly; see
[CSV queue operation](csv-queue.md).

## Validation performed

The production Compose model and both Nginx configs were validated. An isolated
stack passed frontend publishing, storage initialization, migrations, backend
health, and all three worker startups. HTTP tests covered HTTPS routing, HSTS,
CSP, secure cookies, CSRF login, admin static files, protected export delivery,
cross-user access denial, and forwarding-header handling. Public lookup request
limits were subsequently removed as requested; only login and authenticated
lookup limits remain. The updated configs passed syntax validation, and 30
consecutive public requests reached a mock backend without throttling while
login limits remained active.
Database dump and CSV/export archive commands succeeded; the dump restored into
a separate empty test database with its fixture records intact. No lookup API
or Discord webhook calls were made. TLS routing used a temporary certificate;
real-domain DNS, ACME issuance, and renewal must be verified on the target host.
